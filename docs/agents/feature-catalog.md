# Feature Catalog 与产品说明书维护规约

项目维护两份面向全局能力盘点的核心文档：
- **`docs/FEATURES.md`**：精炼版主要功能总览（模块与关键代码索引）。
- **`docs/PRODUCT_MANUAL.md`**：Wiki 结构的完整产品说明书（面向用户的分章节功能说明、交互路径与快捷键速查）。

## 1. 文档结构

1. **第一部分：核心基础功能（来自 `115master` 与 `115master-fusion`）**
   - 记录自上游继承的三大界面底座（U1/U2/U3）、MASTER 播放器、基础字幕、基础刮削与基础打点能力。除非移除或彻底重写上游模块，否则保持稳定。
2. **第二部分：本新版（`115 master fusion+`）新增核心大功能模块**
   - 按功能域归类记录本仓库维护以来新增的所有重要功能模块与关键特性。

## 2. 自动更新触发条件（必须同步更新）

当同一次开发任务包含以下任意一种 **主要功能变更（Major Feature）** 时，Agent **必须在提交代码前同步更新 `docs/FEATURES.md` 第二部分及 `docs/PRODUCT_MANUAL.md` 对应章节**：

- 新增独立页面、视图、浮窗或重要侧边栏/面板模块；
- 新增刮削数据源、字幕源、缓存/云同步机制或导入导出能力；
- 新增用户可见的偏好设置项、筛选维度、批量操作能力或核心交互工作流；
- 对既有大功能模块做显著能力扩充（在该模块的列表下追加或更新对应要点）。

## 3. 无需更新的场景（保持文档精炼）

以下改动**不写入** `docs/FEATURES.md`，避免总览退化为流水账 Changelog：

- 纯 Bug 修复、边界条件修补、防闪烁/层级/样式微调；
- 纯内部代码重构、性能优化（无新增用户感知能力）、类型清理；
- 仅补充单元测试、Storybook、E2E 用例或工程脚本微调。

## 4. 编写与提交流程规范

1. **优先归并到既有模块**：若新功能属于第二部分已有的 `2.x` 模块（如影视库筛选、去重清理、多源刮削、缓存同步），直接在该小节下新增或更新 bullet，不要拆碎成过多零散小节。
2. **独立新域才新建小节**：当引入全新业务域（如全新的外部服务集成、独立工具中心）时，在第二部分末尾按序新增 `### 2.X 模块名称` 小节，并附上 `关键代码` 路径。
3. **提交前自检**：执行 `git commit` 或 `pnpm ship` 提交 `feat(...)` 类主要功能时，将 `docs/FEATURES.md` 与 `docs/PRODUCT_MANUAL.md` 一并纳入同次提交。
4. **定期巡检**：在每次大版本整理或用户要求梳理功能时，对照 `docs/FEATURES.md` 与近期 `feat(...)` 提交检查 `docs/PRODUCT_MANUAL.md` 的章节完整性与准确度。
